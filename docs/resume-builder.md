# Possibilities resume builder

## Scope and entry points

The authenticated child route is `/career/possibilities/resume`; `/resume` still opens Continue Journey. The workspace sidebar presents **Possibilities** as a collapsible parent, matching Learning & growth, with **Explore possibilities** and **Resume builder** children. Search, collapsed-menu expansion, mobile drawers and the focused editor menu use the same hierarchy; only the current child receives the active-page marker. Possibilities exposes Generate resume without a selected skill. The existing Add to Skill Path action is a separate button beside the matched-skill disclosure, retaining its previous save/navigation protection.

The editor recreates the official visitor editor’s compact workbench using this project’s common controls and brand. It uses a top toolbar, continuous left-hand editing and a continuous actual-PDF preview on the right, with CV / Design / Settings tabs and a YAML switch. The official online frontend is not published; no bundled online code, iframe or official example-person data is used. It supports all nine entry types and built-in themes, nested list controls, safe model-derived Design/Settings fields and advanced locale settings through YAML, PDF/YAML downloads, selective AI chapter replacement, 50-step in-memory Undo/Redo and the persistent AI undo snapshot. The heavy editor is lazy-loaded. There is one current draft per account; changing target requirements warns the user to export and only replaces the target when a proposal is applied.

Explore possibilities requires a valid selected occupation before Generate resume can be clicked (skill selection is not required). The account-isolated selection is saved before navigation. Resume builder loads the selected occupation and all its required WEF skills from the authenticated `/api/v1/possibilities/{occupation_code}/requirements` endpoint; it has no editable job requirements or example shortcut. Change target role returns to Explore possibilities. Missing, invalid or empty roles show a recovery prompt and block generation without removing an existing resume. Opening the page never invokes AI.

Generation candidates come from three sources: explicit original-resume skills, current confirmed platform/personal/specialist skills, and skills associated with every course saved in My courses (not started, in progress or completed). Confirmed teaching-objective skill choices from those saved courses are included too. Pending course plans, standalone learning goals, career shortlists and unconfirmed learning intentions do not independently contribute skills. Reviewed practice can support an included skill and remains resume evidence, but does not add a fourth source. Course mapping failures block generation instead of dropping names or treating course titles as skills.

The current frontend sends `skill_selection: aggregate`. The server retains every supplied skill, deduplicates normalized names, and preserves complete original labels as independent bullets. It performs no role relevance selection, including on AI timeout or invalid output. Career objectives and factual polishing still use the selected role; skill associations and gap recommendations are not generated in this mode. Results use `skill_filter_version: all_sources_v1` in the existing version field for draft compatibility. Older API clients without the new selection mode retain their legacy relevance behavior. No candidates and no reviewed evidence disables generation with an add-details prompt. The separate Open an empty template action remains a manual, local editing option and never calls AI or courses.

Review AI suggestions offers Select all / Deselect all as well as individual chapter selection. Skills only replaces the current chapter after the user applies it. Existing drafts remain readable; pending suggestions from the earlier rule are invalidated by the versioned input fingerprint. Generate and apply Skills to migrate an existing resume to the combined list.

Target & AI shows the combined skill names and counts from the original resume, confirmed skills and all saved My courses. Overlaps are deduplicated. Existing documents are compared with the current candidates, including restored drafts already marked `all_sources_v1`; missing skills show a Review skill updates action. Uploading a source or saving a course does not silently overwrite the editor. Generate new suggestions and apply Skills to update the document and its asynchronous PDF preview. If all mapped skills already exist, the panel says so rather than implying the course must produce a new skill. Optional teaching-objective skill extraction remains separate.

Vite prebundles the worker's PDF.js and Mammoth imports at startup. Discovering these dependencies only on the first upload otherwise causes a development-page reload, dropping an unfinished import. The browser acceptance also checks that uploading does not navigate the main frame.

`frontend/tests/resume-course-skill-updates.browser.mjs` covers saved-course changes with an existing local resume, complete request/response/application skill coverage, pending-state recovery after reload, undo/redo, PDF readiness and desktop/mobile layouts against the synthetic provider. It accepts `AIW_QA_SOURCE_PDF` for a local fictional PDF fixture; otherwise it uses a synthetic DOCX. No live provider calls are made.

Uploaded and manually entered source details are editable immediately: personal fields, original-resume skills, and experience/background text remain visible. There is no separate source privacy-review checkbox or confirmation gate. Clicking Generate uses the latest edited source, including older local drafts whose legacy `source.reviewed` flag is false. Current requests use `evidence_mode: auto_redacted` and `evidence_reviewed: false`; automatic contact redaction and source validation remain active. Course-skill choices, learning-record confirmation, generated-chapter application and the final interview review remain separate workflows.

## Local data and privacy boundary

`infrastructure/storage/resumeStore.ts` owns a separate IndexedDB database `aiwrevolusi.resume.local.v1`, with a `drafts` object store keyed by authenticated account ID. The record holds pending/current job requirements, the original Blob, reviewed/redacted text, local contact mapping, reviewed source skill names, optional source project metadata, generation-input fingerprints and applied Skills-filter version/fingerprint, document, raw YAML, last successfully rendered document for preview recovery, proposal, undo snapshot, gaps and optional recommendations. It is **not** an accountStorage/workspace sync key and has no database table or persistence API.

- Every edit queues an atomic transaction. Only completed writes display Saved on this device.
- Revision checks stop stale tabs from overwriting newer records. Malformed records are preserved until the user explicitly clears them.
- Logout/account change unmounts the account-keyed editor, aborts pending requests and drops in-memory previews. IndexedDB survives logout.
- Clearing drains writes, blocks concurrent edits and deletes only that account's resume record.
- Missing/quota-blocked storage shows a warning and keeps the current in-memory document editable/exportable; recovery is not promised.
- Same browser and same site only. Clearing site data, private browsing expiry and browser eviction can lose drafts. Account namespacing is not device encryption.

PDF/DOCX originals are never uploaded. PDF.js and Mammoth extract **text**, not imported HTML, inside a dedicated parsing worker. PDF.js uses an explicit nested worker port (automatic browser initialization assumes window/document). Limits: one file, 10 MB; PDF 20 pages; extracted text 60,000 characters. DOCX central-directory and actual streamed inflation are both bounded (40 MB total, 10 MB per entry, 2,000 entries); encrypted/path-traversing/duplicate/malformed ZIP entries fail. No OCR or password collection. Contact redaction and Skills-block extraction run locally. Users can correct the extracted fields without a separate privacy confirmation. Automatic redaction is not comprehensive; the backend still validates contact-free evidence and source references.

The original My Plan file controls route PDF/DOCX into the local repository and keep the unsubmitted form intact. TXT/MD/CSV retain their existing reference workflow. A My Plan resume never enters synced `resources`. The resume page reads the same repository but still requires job requirements.

Skills merge confirmed skills, My courses skill mappings and explicit original-resume skills. Course selections do not claim mastery, credentials or completion and do not change other pages' skill-state rules.

Original-resume extraction scans every explicit Skills block, including repeated Technical/Soft Skills headings, competency/expertise headings and inline lists such as `Skills: SQL, Python`. Recognized first-line headings are not treated as a personal name during redaction. Automatic extraction is rederived from stored source text; manually edited skill lists remain authoritative, including deliberate removals. Existing generated documents change only when the user generates and applies Skills again.

Assistant edits validate that existing skill identities survive wording changes, reordering and deduplication. Generic polishing, shortening or role alignment cannot delete distinct skills. Explicit removal of named skills or the complete Skills section remains supported; failed retention validation uses the existing single correction attempt and otherwise leaves the document unchanged.

Ordinary assistant updates may omit `source_ids`; the server binds them to the exact existing `entry_id`. Explicit references still undergo the same target-first, own-entry-only checks. Shared grounding errors are translated from assembled document positions to compact patch positions before the single correction, with fixed guidance and original target IDs, never the rejected prose. Provider timeout logs distinguish upstream errors from the total-budget phase without recording document content. The assistant presents a retryable output-failure message rather than asking users to repair model citation IDs; structured diagnostics remain in the API response.

## Transient authenticated endpoints

| Endpoint | Input / output |
| --- | --- |
| POST `/api/v1/resume/generate` | Job requirements, candidate skill IDs/names, optional reviewed redacted evidence -> English chapter proposal, source IDs and gaps |
| POST `/api/v1/resume/recommend-courses` | Gaps -> up to five validated catalogue course IDs, gap IDs and reasons |
| POST `/api/v1/resume/render` | Complete structured RenderCV document -> binary PDF |
| GET `/api/v1/resume/capabilities` | Non-secret configured provider hostname/model and pinned renderer version for disclosure |

Use the existing `AI_API_KEY`, `AI_BASE_URL`, `AI_MODEL`, `AI_API_MODE` and optional `AI_EXTRA_HEADERS` configuration. A missing explicit key disables resume generation, not manual editing/rendering. Resume AI constructs a separate configured provider with keyless disabled, no fallback chain, no content cache and no retries. Other AI features retain their previous gateway behavior. No real supplier request is needed by offline tests. Third-party retention policies still apply; the UI does not promise zero supplier retention.

No original evidence means Skills only. Each AI entry must cite supplied skill/fact IDs; non-skill chapters require original facts. Full generation assembles one complete Skills section as one independent bullet per complete skill label (up to 250 candidates, 160-character names and one skill reference per entry; other sections and assistant edits retain 80-entry limits); it never silently truncates. Shared partial-entry grounding stays independent so assistant edits do not need to cover every skill.

Generation accepts optional `source_projects` records with `id`, `mode`, `fact_ids`, immutable `name`/`date`, and ordered `highlight_fact_ids`. New clients always send the array, including when empty. Local parsing works from redacted evidence and recomputes on edits. Clearly identified projects are reviewed with their original individual highlights; ambiguous sections are passed through unchanged, without guessed metadata or AI polishing. Responses optionally include `project_id` and a `project` (`name`, `date`, `highlights`), applied as RenderCV normal entries rather than a flattened bullet. The server rejects new projects, changed identities/dates/numbers, merged highlights, cross-project references and project facts recast as employment. Existing requests and drafts without these optional fields remain readable. Automatic grounding remains conservative rather than a proof of semantic factuality; users must review suggestions.

Changes to target, reviewed evidence or skill inputs invalidate in-flight generation and unapplied proposals using account-scoped input fingerprints. Existing content and its applied interview target stay unchanged until selected suggestions are applied; undo restores content, not the upstream selected occupation.

Recommendations are independent of generation. They shortlist actual catalogue titles/descriptions/outcomes and skill tags, then use the configured provider only to select from that pool. IDs/gap links are rechecked and deduplicated on the server; weak tag-only matches are excluded. Empty results and DB/provider/query failures return an empty list, so the UI quietly omits the optional area. Selection uses the existing `changeSavedCourses` operation. Only normal course/plan selections sync, never requirements/evidence/resume content. A local course addition does not claim that account sync already completed.

Resume responses, including validation/auth failures, use `Cache-Control: no-store`. Validation errors do not echo rejected request values. Logging records status/timing/error category, not bodies or exception strings containing private values. Rendering does temporarily receive the complete document (including personal fields), separately from redacted AI input; the UI explicitly discloses both transfers.

## Actual RenderCV/Typst rendering

The Python dependency is locked to `rendercv[full]==2.8`. The worker uses its actual model builder, theme templates and Typst PDF compiler, not HTML printing. Each request gets a parent-owned temporary directory, fixed filenames, explicitly UTF-8 JSON input and a short-lived process. Default timeout is 25 seconds; at most two workers run per application process. Compiler package files are inside the same request directory, so success/failure/forced timeout all remove them. PDF responses are bounded to 4 MB.

Only built-in themes and safe design/settings fields are permitted. Custom themes/templates, photos, output paths/commands, prototype keys, raw Typst/math code, file links and embedded resources are rejected. The public renderer adds a literal Markdown/quoted-link boundary instead of the CLI's intentional raw-Typst passthrough. Native font and package resolution uses installed/bundled assets only; user fields cannot provide imports or resource paths.

The published 2.8 wheel bundles RenderCV's Typst package but not its FontAwesome dependency. The pinned official MIT `fontawesome:0.6.0` package is vendored under `app/data/resume/preview/fontawesome/0.6.0`, including LICENSE and SOURCE.json with upstream attribution/checksums. The exported frontend schema preserves the pinned upstream licence in RENDERCV-NOTICE.txt, also shipped in public/licenses. Python package-data includes it. All nine themes have actual offline PDF regression tests, including a nameless Skills draft and a multi-page document.

PDF.js CMaps, standard fonts and WASM are copied from the committed frontend dependency lock by `scripts/pdfjs-assets.mjs` during predev/prebuild. No CDN resources are used. Do not bypass those hooks when launching Vite manually unless the assets have already been generated.

The shared schema and `rendercv-2.8.controls.json` control metadata are exported from the **installed pinned version**, not GitHub main:

```powershell
backend/.venv/Scripts/python.exe scripts/export_resume_schema.py
```

The isolated worker uses context-aware escaping for quoted template data (including PDF title, name and separators). Only the two engine-owned footer page-counter expressions remain executable Typst; user strings still pass the original safety validation and Markdown escaping. This preserves real page numbers rather than printing internal code.

The exporter removes only invalid non-string title/description annotations emitted by 2.8; it does not remove validation constraints. Form/YAML share the same document. Invalid/unknown YAML stays as raw local text, disables destructive form/AI changes, and retains the last valid preview, including reconstruction from the local successful-render snapshot after reopening. Rendering is debounced and abort/version guarded; download uses the same bytes as the current valid preview, never a stale response.

## Editing workbench details

- A resume document activates route-local focus mode: the project sidebar, normal page header and footer are hidden. The toolbar’s workspace-menu button opens the existing navigation drawer. Returning to another route restores the original global sidebar preference without rewriting it. Account/sync alerts remain visible above the workspace; the editor fits the remaining viewport height, and the backup action wraps on narrow screens.
- The panes start 50/50 with a pointer/keyboard separator (Left/Right; Home resets). The actual workspace width, not device identity, controls the Edit/Preview layout below 900px. Both panes scroll independently; long CVs never make the document body scroll sideways.
- CV shows personal fields followed by every chapter in document order. Chapters collapse, rename, reorder and confirm before deletion. Entries and Highlights/Authors/Social networks/custom connections have individual list controls. Empty inputs never import fictitious facts.
- Bold/Italic/safe-link formatting requires a selection in a Markdown-capable CV field. It is disabled in YAML, Design and Settings. Input grouping uses a 500ms window per field; structural actions have separate history steps. History is account-local memory, capped at 50; reopening starts a fresh memory history while the existing AI undo snapshot still survives.
- Model metadata supplies each theme/language’s effective defaults. Viewing tabs does not add defaults to YAML. Only edited paths are written, with special handling for prior scalar typography overrides. Explicit overrides and unknown YAML are retained; there are no photo, remote resource, custom template or command/path controls. Locale has no dedicated form tab: new drafts use English defaults, and advanced users can edit `locale` in YAML. Existing locale overrides survive form edits, reopening and rendering unchanged. Locale changes fixed labels/date wording only, not user facts or generated-language rules.
- RenderCV 2.8 defaults make text-based chapters unbreakable through `entries.allow_page_break`. For an unusually long Skills/Text chapter, explicitly enable Design → Entries → Allow Page Break; this preserves the pinned theme defaults rather than silently rewriting them. The long-document regression uses that real exported control.
- The PDF preview keeps page placeholders for a continuous document and renders only visible/adjacent canvases with a pixel budget. It supports page jumping, fit width and zoom. Rendering cancels obsolete work and uses the same valid PDF bytes for downloading.
- Target & AI opens the existing requirement/source-review workflow in a dialog. Courses opens a focus-trapped right-hand drawer only when actual recommendations exist. Resume options holds YAML export, persistent Undo AI changes, privacy details and confirmed local clearing. Existing storage/API formats are unchanged.

### Free-text contact fields

Email, phone and website are optional free-text fields, not format-gated inputs. The editor and original YAML retain exactly what was entered, including local phone numbers and website labels without protocols. Blank scalar values and list rows are omitted from the render-only copy. The isolated worker keeps these values outside RenderCV's typed contact validators and renders them as escaped Typst string literals, preserving header order, existing social/custom connections and list order. Contact strings are not parsed as Markdown/code or turned into automatic hyperlinks; other content retains the existing safe-link/code restrictions. No country code, URL prefix or substitute contact is invented. The phone-number-format design control is hidden because literal phone text is no longer automatically reformatted. Only basic text/list structure and size limits apply, with no additional saved fields or API changes.

## Generation correction and private diagnostics

Normal reviewed English ability wording (including Able, Skilled, Comfortable and Familiar) no longer fails merely because of capitalisation. Reviewed generic past-tense words still need cited facts; references, names, numbers, credentials and executable/resource content remain constrained. This is a conservative heuristic, not a guarantee of semantic fact verification.

New clients submit `source_sections`, `source_projects` and `occupation_code`. The server reuses the same uncapped database requirement/card mapper, validates the exact requirements text and reviewed section/fact ownership, and builds selected Skills and project identities deterministically. At most one asynchronous `resume.polish.v3` call returns fact-ID text patches plus short candidate-ID decisions anchored to server-owned role requirement IDs (or null for unrelated), not another whole resume. Requests without `occupation_code` retain the existing v2 flow. Each patch is independently grounded; rejected or omitted patches retain reviewed original text. Unclear projects and non-polishable source paragraphs never go to AI.

The call has a cancellable 60-second wall deadline, with a 70-second browser budget. Browser abort/disconnect cancels the upstream HTTP coroutine and closes its client. Timeouts, transient transport failures and invalid model output return an explicit `outcome: source_preserved` with fixed-code `notices`; invalid input, configuration/access errors and internal errors are not disguised as success. Role-filtered source-preserved results contain only standard-confirmed relevant user Skills (uncertain semantic candidates are excluded), original structured/raw projects and all reviewed source sections, including supported original additional headings. While generating, the UI shows a blue/lilac indeterminate progress bar, understated elapsed time and Cancel generation; no completion percentage is fabricated and reduced-motion preferences are respected. Results display the preservation reason. Existing resumes change only after selected chapters are applied. Source preservation never changes the applied/interview target or requests new gap courses.

Legacy requests without `source_sections` retain the existing strict full-response validator and at-most-one correction in the shared 45-second budget (55 seconds in old clients). Editing-assistant partial grounding remains unchanged. Neither flow caches private payloads or uses hidden transport retries.

Errors keep their string `detail` and HTTP status, adding optional `code` and `fields` (up to five paths of fixed schema keys and numeric indices). Chapter names and unknown field keys are not returned; the browser resolves numeric chapter positions from its local document. RenderCV errors preserve the previous valid PDF and the user's YAML. Render requests remain debounced and run again only after a document change or explicit retry. Free-text contact behaviour is unchanged. Logs contain fixed codes, attempts, status and elapsed time, never resume or generated content. Current access logs alone do not identify the user's earlier 422 cause; these diagnostics locate future rejections without guessing or weakening RenderCV validation.

## Legacy role-relevant Skills contract and acceptance

- `occupation_code` is optional for compatibility; the current page always sends it. Unknown/empty roles and reference database errors are explicit recovery errors. A requirements mismatch returns `target_role_changed` (409), with Retry role requirements; it never calls AI against stale inputs.
- `skill_filter_version: "role_relevance_v1"` marks the generation result. Every pending candidate needs exactly one valid reference/null decision. Unknown candidates/requirements, duplicates or omissions exclude that affected candidate and emit `skill_relevance_incomplete`; already-validated text patches and other decisions survive. Direct standard matches cannot be deleted by AI. No association is not proof of a missing ability; uncertain/excluded candidates do not create new gap claims.
- The 60-second backend/70-second browser budgets, one-call cap and real cancellation remain. Whole-call timeout/transport/parse failure preserves reviewed facts and only direct mapped skills. Configuration, authentication, invalid sources and internal errors remain errors, not fallback successes. Logs contain only codes/counts/outcome/timing, not private text.
- `no_related_skills` with reviewed non-Skills evidence returns an explicit empty Skills proposal, allowing generation without that chapter. Applying that selected chapter deletes the old Skills key; not selecting it keeps the old list and its previous filter proof. No related skills and no reviewed non-Skills content returns `no_related_input` rather than an empty generated resume.
- Fingerprints include the filter version, current role, all candidates and reviewed sources. Old-rule or stale un-applied proposals are cleared, not the saved resume. Applied Skills proof changes only when Skills is applied; manual/assistant Skills edits invalidate it. Partial chapter application displays an unapplied-filter warning. Undo/redo/AI undo restore proof and content while preserving the current role selection. Source-preserved results never advance the applied interview target.
- `test_resume_relevance.py` covers standard/semantic matching, malformed decisions, no invention, single-call cancellation/fallback, 1/80/81/250 independent skills, server reference errors and route binding. `resume-relevance.test.mjs` covers empty-section application, proof/history/legacy records and the 70-second wire contract. `resume-relevance.browser.mjs` uses synthetic-only auth/DB/AI with the real local generator to exercise all skill sources, selective filtering, unchanged sources/profile/learning, reference retry, conservative fallback, partial/empty application, undo, PDF export, cancellation and stale-account isolation. Artifacts stay ignored under `.local/resume-qa/role-relevance/`; this does not claim hosted or live-provider validation.


## Direct-execution editing assistant

The editing assistant sends immediately on the send button, Enter or Ctrl/Cmd+Enter; Shift+Enter inserts a newline and IME composition never submits. Shortcuts execute directly while retaining unsent composer text. A synchronous guard prevents concurrent requests, but users can compose their next instruction while an edit runs. There is no pre-send context-review modal or proposal-approval step. Every server-grounded change is restored and the complete resulting document is checked before one atomic update. Changes apply before the PDF finishes refreshing. Cancel/failure retains the failed instruction with Retry and preserves any newer composer text; undo/redo and stale-request protection remain active.

The assistant chooses concise professional editorial defaults instead of asking questions or offering choices. General optimization improves wording/readability, shortening removes redundancy, and role-focused skill edits preserve existing skills. Missing facts cannot be invented: supported portions can be applied with a fixed limitation notice. Feedback is computed from actual changed sections/entries/design fields, never displayed from model prose. Explicit no-change and unsupported results have distinct statuses and create no undo step. Question-only responses, claimed edits with no effective patch, and contradictory result types receive the existing single correction; repeated invalid output is an error, not a successful no-op.

New `/resume/assist` clients use optional `context_mode: "auto_redacted"`, without claiming manual `context_reviewed`. Optional `target_context` carries the redacted career context separately from the instruction. Responses add optional `result_kind` (`edit`, `no_change`, `unsupported`) and `limitation` (`missing_facts`, `unsupported_edit`); previous callers and local drafts remain compatible. Both modes retain contact, source-ID, safe-field, factual and design validations. Assistant-only budgets are 90 seconds total on the server / 100 seconds in the browser, with the initial request and at most one correction sharing a single deadline; the 60/70-second whole-resume generation path is untouched.

Personal headers never leave the page. Known private values are replaced across sections, instructions, target context and conversation history, then restored locally using a request-scoped mapping. There is no Privacy options disclosure or custom private-term input. Chat lives only in the account-keyed component and is cleared on navigation/unmount/account change. Automatic redaction is not comprehensive; supplier retention policies still apply.

Each applied assistant result creates one independent editor history step and the existing persistent AI undo snapshot. Skills edits invalidate prior role-filter proof; Undo/Redo restore content and metadata. The chat Undo action is offered only for the assistant's latest still-current applied result and matching previous snapshot, so it cannot undo unrelated edits. Uploaded source, unrelated chapters, personal fields and applied role context remain unchanged.

Requests capture account/session, document revision, skills, applied role context plus the current selected-target key (without replacing the applied interview target) and model preference revision. Cancellation or an input change aborts client waiting and rejects any late result; failures never auto-resubmit. The async assistant races the edit task with a direct ASGI receive/disconnect listener. Cancel, input changes or account changes abort the browser fetch; disconnect cancels and awaits the upstream HTTP coroutine and closes its client. It does not use a threadpool or is_disconnected cancel scope. Uploaded-source review and whole-resume generation proposals remain separate and still require their existing review/application.

`resume-assistant.browser.mjs` covers direct keyboard/click execution, no modal/proposal UI, immediate progress, one atomic apply/undo/redo, no-op and mixed-change rejection, automatic personal-data/history redaction, cancellation, manual/model edits, reload/session cleanup, real PDF and mobile overflow. The test uses synthetic providers/accounts with the real local renderer; it is not a live supplier or deployment test.


### Compact assistant edits, shared deadline and safe errors

Production `/resume/assist` uses `assist_resume_async` and the private `resume.assist.entries.v2` contract. Public `AssistRequest`/`AssistResponse` and old manual-review clients remain compatible. The synchronous helper is retained only for legacy test callers, not the route. Whole-generation 60/70-second, legacy-generation 45/55-second and PDF budgets are unchanged.

- Conservative local scope detection sends only explicitly targeted sections, or design settings/allowlist for design-only instructions. General, mixed or context-dependent requests keep full context. Skills candidates are omitted from section requests that cannot edit Skills. Only the last two complete conversation pairs are sent; design-only requests omit history and career context too. Original section indices and short `eN`/`kN` references never shift. Server validation retains the complete original document and rejects out-of-scope edits. The AI emits changed prose fields or individual highlight indices, with legacy full-entry patches still accepted, explicit deletion IDs and optional complete order lists. The server restores unchanged fields and entries; omission is not deletion.
- Updates must cite their own target entry first. They cannot cite another project/experience or borrow facts from other entries. Existing nine entry types, identity/date fields, quantities and private placeholders are preserved. Unknown, duplicate, cross-section and conflicting references, incomplete order lists and over-limit sections are rejected before the existing fact/contact/claim/RenderCV checks.
- Skill additions contain only supplied user-skill references. The program restores the exact canonical names as independent bullets (or preserves an existing text-entry section). Additions to Experience/Projects are not allowed. Assistant sections stay limited to 80 entries; no truncation.
- A 90-second async wall deadline includes initial call, validation and one optional correction. Each default/override upstream request receives only the remaining budget, bypassing the provider's legacy 45-second initialization. Every request has zero transport retries, no cache and no model rotation. Correction handles schema/reference/fact errors and invalid direct-edit outcomes, uses the same model, original scoped sources and fixed code/path feedback, and is skipped with under 5 seconds left. Invalid content is never fed back as evidence.
- Wall/read timeouts return HTTP 504 / `ai_timeout`: `AI editing timed out. Your resume is unchanged. Try again.` Transport failures use `ai_connection_failed`; unavailable upstream HTTP responses use `ai_provider_unavailable`; rejected credentials, configuration, rate limits and request rejection have separate fixed codes. Invalid output/safety changes return 422 with fixed diagnostics; unexpected internal errors return 500. Provider error bodies are not shown or logged. The browser's independent 100-second expiry maps to the same timeout message; active cancellation remains cancellation.
- Only fully validated assembled results reach the client's existing atomic auto-apply and single undo step. Failed/cancelled/stale requests do not change the document, prior undo snapshot or PDF. Uploaded-source review and whole-resume-generation suggestion review are unchanged.

### Assistant response efficiency

Exact wording/shortening presets use a conservative `content` scope and the smaller `WordingAssistResponse` contract. All current sections and their original IDs remain available with only their prose fields; identity/date metadata, unrelated career requirements, design settings, design paths and candidate skill additions are omitted from the provider request. Every existing Skills row remains available. The last two complete conversation pairs remain available for previous user preferences. Mixed, general or context-dependent instructions retain the general contract and full context. Content/section scopes skip constructing design paths.

Wording responses may contain only changed existing prose fields, individual highlights keyed by zero-based string index, or a replacement string for an existing plain-string entry. They cannot delete/reorder entries, add skills, edit factual fields, emit source IDs or edit design. The program binds each update to its own original entry, restores unchanged fields, and runs the existing type, number, fact, privacy, skill-retention and full RenderCV checks. The public API and stored drafts do not change. The general private contract continues accepting full-entry/partial-field patches and its existing deletion, reorder, skill-addition and design operations. Schema failures, ineffective edit claims and questions retain at most one correction using only the original sources and fixed feedback. Normal success still uses one call with the current selected model and the existing shared 90-second deadline.

`test_resume_assistant_speed.py` checks that a single changed highlight in a nine-highlight entry produces 652 versus 147 output bytes (77.5% smaller), with identical assembled results. A 50-entry section with one changed entry requires one grounding check instead of 50. `test_resume_assistant_wording.py` measures all provider prompt text including schema for the same synthetic request: 11,401 versus 6,183 bytes (45.8% smaller). It also exercises actual default/override HTTP requests, no-change/unsupported results, correction, forbidden operations, fact/skill preservation, cancellation and shared deadlines. These are deterministic size/check-count comparisons, not model-latency claims.

Synthetic-only live testing with a fuller resume and recent history on `deepseek-v4.1-flash`: the generic contract used 15,753 prompt bytes, 8,710 payload bytes and completed in 10.62 seconds. The final wording contract, through the browser-selected-model `PriorityProvider` path, used 9,785 prompt bytes, 6,398 payload bytes and completed in 10.31 seconds (9.94 seconds upstream), with one call and successful grounding. These isolated variable samples are not a controlled latency benchmark or proof that an external supplier cannot time out. The user's reported 90-second first-call timeout was not reproduced with the synthetic fixtures; confirmation with the original local draft remains separate.

Production logs retain byte sizes, scope, the actual default/first browser-selected model ID, sent-entry/update/partial-update counts and upstream/validation/total timings without resume text. Timeout and upstream-failure warnings include model, scope, input bytes and sent-entry count so failed requests can be compared with successful smoke checks. Model labels are validated to prevent multiline log injection; provider URLs, headers and resume text are not included. The browser regression covers both wording/shortening shortcuts, partial highlights, preserved metadata, direct apply, undo/redo, cancellation/errors, saved drafts, desktop/mobile and real PDF output.

### Career evidence tailoring (Epic 8)

New generation clients send `source_metadata.version=career_evidence_v2` with per-candidate multi-source origins and explicitly selected/reviewed learning facts. Existing `skills`/`evidence`, old requests, generated responses and drafts remain readable. Unapplied old-rule proposals are invalidated by the new input fingerprint. Assistant grounding and all independent budgets stay unchanged: generation 60/70 seconds; assistant 90/100 seconds.

The authenticated requirements API returns optional `tasks` from the same occupation row and existing skill mapping used by the card. The server independently reloads the occupation by code. Career tasks are reference context, never personal evidence. `resume.career.v2` uses one cancellable async supplier call for fact polishing, candidate classification, a maximum of two short background fragments, quoted evidence associations and a complete project permutation. The program supplies `Career objective: <role>`; fragments pass the existing strict number/name/action/substantive-word guard. Learning intentions and completion records are excluded from summary achievements. Invalid parts retain the original reviewed text and fixed notices. No additional provider call or default model change is introduced.

Skills stay independent full-name bullets, with no PDF state badges. Sorting prioritises reviewed examples, then reviewed/user-confirmed skills, then learning intentions; standard mappings precede model semantic judgments within a tier. Origins survive deduplication. An exact quoted reviewed example establishes that a source exists; semantic interpretation still belongs to the model and is labelled as such, not as an independent assessment of competence.

Reliable projects may move only as whole records using a full unique permutation. Identity, dates, all numbers, individual highlights and fact ownership remain intact. Any verbatim project locks the original order. Work history remains in source order. Timeouts/unavailable/unparseable output use the existing conservative standard-mapping-only Skills fallback, preserve original source text and do not advance the applied interview target.

`Learning records` is a closed disclosure in the existing source-review card. Catalogue completeness checks chapter count, unique sequential chapter orders and nonempty chapters; completion uses only synchronised rows, requiring every zero-based chapter value to be exactly 10/10. Pending local drafts never certify completion. A course is explicitly self-recorded, not a certificate or proficiency assessment; the API has no completion date and none is inferred. Existing study/course/workplace practice descriptions keep their nature and date. Initial generation and subsequent regeneration both produce chapter suggestions; even the first document is created only after explicit review and application. Users select and review/redact each description before it becomes evidence in `Professional Development` or `Learning practice`; no project/employment/certificate is invented. Unreviewed/changed/unavailable selected records block generation with a visible explanation. Catalogue or progress failures offer retry, and optional learning-data failures do not disable a CV flow that has no selected learning records or unresolved course skills.

`role_alignment` and `tailoring_version=career_evidence_v2` accompany modern results. The closed Career alignment panel lives in the editor's scrolling pane and in generation review. It shows the requirement, original candidate, all origins, exact reviewed source and actual chapter/entry locations, standard versus semantic status and counts. It provides no match percentage, ATS score or hiring prediction. An unlinked requirement says current information provides no support, not that the user lacks the ability. Applied metadata is fingerprinted to the actual document; partial apply filters locations to selected chapters, manual/assistant content changes require rechecking, and editor/persistent AI undo restores the earlier explanation. Learning/role changes invalidate only pending generation, not the existing CV or applied interview context.

### Task relevance and reviewed curriculum skills

Modern requests use `career_evidence_v2` and results use `role_relevance_v2`. v1 clients, drafts and responses remain readable. The occupation requirements response retains `tasks` and adds stable, occupation-bound `task_references` plus `reference_fingerprint`. Generation independently reloads and verifies the snapshot sent by the client. Exact standard matches are protected. The single existing AI call may link other actual user candidates to one career skill ID or one concrete task ID, or mark them unrelated. Unknown, cross-role, duplicate or missing decisions are excluded with fixed notices. Output components are checked independently, so rejected wording cannot erase valid relevance decisions. Timeout fallback remains standard-mapping-only and does not advance the applied interview target. Coarse recommendation-card counts are unchanged and do not cap CV skill count.

Inside Learning records, `Skills from your courses` lists saved, pending and synchronised-progress courses, preserving their IDs even when titles match. Nothing is extracted automatically. Click `Identify learning skills`, inspect each exact teaching-objective quote, select the desired names and confirm the source review.
